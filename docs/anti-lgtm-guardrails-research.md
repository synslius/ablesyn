# Anti-LGTM Guardrails: 3 Expanded Visionary Research Directions

## Intent

This memo proposes the next slice for ablesyn with a strict anti-LGTM posture: no confidence upgrades without hard evidence, no "looks good" merges without machine-verifiable checks, and no narrative-to-substrate jumps.

---

## Direction 1 — Evidence Ledger + Verifiable Claim Lineage

### Why this matters next

Today, ablesyn can express uncertainty well, but it still depends on operators to verify whether evidence really backs a verdict. The next critical slice is **cryptographically anchored claim lineage** so every `PASS`, `FLAG`, and `BLOCK` can be traced to immutable evidence pointers and reproducible probes.

### Research question

How can we make verdict inflation computationally expensive and evidence regression immediately visible?

### Proposed capability

Add an evidence-ledger layer that:

- assigns each evidence artifact a content hash and timestamp;
- links each claim revision to prior revision hashes;
- records which probe execution produced which evidence;
- forbids verdict promotion (`FLAG -> PASS`) unless policy-required evidence hashes exist.

### Technical design sketch

1. **Canonical claim digest**
   - Deterministic canonicalization of `.able` claims.
   - Hash root committed with every change.
2. **Evidence manifest schema**
   - New schema for evidence items (`kind`, `source`, `hash`, `collected_at`, `collector`, `repro_cmd`).
3. **Lineage policy engine**
   - Declarative rule set: e.g., substrate claims require at least one runtime metadata artifact plus one independent probe.
4. **Tamper-evident CI gate**
   - CI fails if a claim hash changes without corresponding evidence-manifest delta and rationale.

### Security and guardrail impact

- Stops silent narrative rewrites from passing as validated truth.
- Makes social "LGTM" insufficient without machine-backed provenance.
- Supports forensic replay after incidents.

### Measurable success criteria

- 100% of verdict-bearing claims include valid lineage chains.
- 0 unauthorized `FLAG -> PASS` transitions in CI.
- Reproducibility: independent runner can replay >90% of probes from manifests.

## Direction 2 — Policy-as-Code Merge Firewall (Anti-LGTM Core)

### Why this matters next

Most security drift enters through merges that are "reasonable" but weakly checked. ablesyn’s future guardrails should enforce that every semantic claim change has matching policy evidence before merge.

### Research question

Can we convert reviewer intuition into strict merge invariants that block unverifiable confidence upgrades?

### Proposed capability

Build a **policy firewall** that inspects diffs to `.able`, schema, parser, and checker logic, then enforces risk-tiered requirements.

### Technical design sketch

1. **Semantic diff classifier**
   - Parse old/new claims and classify changes: confidence increase, verdict change, layer change, probe removal, evidence weakening.
2. **Risk matrix**
   - Map change classes to mandatory checks.
   - Example: `SUBSTRATE` claim added => require runtime probe artifact + secondary reviewer + passing parser/checker tests.
3. **Merge contracts**
   - PR must include a machine-readable "change contract" generated by CLI.
   - Contract enumerates risks, required proofs, and statuses.
4. **Exception protocol**
   - Time-bound, signed waivers only for emergency patches.
   - Auto-expire and trigger follow-up hardening issue.

### Security and guardrail impact

- Turns human review from subjective sign-off into policy verification.
- Prevents high-risk semantic drift hidden in small text edits.
- Establishes anti-LGTM as an enforceable system property.

### Measurable success criteria

- 100% high-risk claim diffs blocked unless contract requirements pass.
- Reduced post-merge guardrail regressions quarter-over-quarter.
- Mean time to detect unverifiable confidence edits: near-zero in CI.

## Direction 3 — Adversarial Probe Harness + Confidence Attack Suite

### Why this matters next

Guardrails are only real if they survive intentional pressure. ablesyn needs a red-team harness focused on how claims get over-trusted under persuasive narrative, multilingual framing, and partial evidence.

### Research question

Which attack patterns most reliably trick systems into upgrading confidence without sufficient substrate evidence, and how can we continuously detect regressions?

### Proposed capability

Create a **confidence attack suite** that generates adversarial claim/probe scenarios and scores the checker’s resistance.

### Technical design sketch

1. **Attack taxonomy**
   - Narrative authority injection ("trusted operator" language).
   - Layer confusion (narrative statements phrased as substrate facts).
   - Evidence laundering (inferred evidence mislabeled as observed).
   - Translation drift (uncertainty dropped in EN/ZH transforms).
2. **Scenario corpus**
   - Versioned set of malicious and near-boundary `.able` fixtures.
   - Includes minimal diffs that mimic real PR smuggling patterns.
3. **Resistance metrics**
   - False-accept rate for unsafe `PASS`.
   - Detection rate by attack class.
   - Time-to-fail in CI.
4. **Continuous adversarial CI**
   - Every parser/checker update runs attack suite.
   - Any increase in false-accept rate blocks merge.

### Security and guardrail impact

- Quantifies robustness against persuasive but ungrounded claims.
- Catches regressions before deployment.
- Aligns future language features with measurable safety budgets.

### Measurable success criteria

- False-accept rate for critical attacks stays below defined threshold.
- No release proceeds when attack resistance degrades.
- Coverage expands with each newly discovered exploit pattern.

## Recommended Next Slice (Execution Order)

1. **Start with Direction 2 (Policy-as-Code Merge Firewall)** for fastest risk reduction in current workflow.
2. Implement **Direction 1 (Evidence Ledger)** to harden provenance and auditability.
3. Scale with **Direction 3 (Adversarial Harness)** to prevent regression and strengthen long-term resilience.

This ordering delivers immediate anti-LGTM enforcement, then deep provenance, then continuous adversarial assurance.

## 90-Day Thin-Slice Plan

- **Days 1–30:** semantic diff classifier + risk matrix + minimal CI blocker for verdict/confidence upgrades.
- **Days 31–60:** evidence manifest schema and CLI generation/validation.
- **Days 61–90:** seed attack taxonomy and 20–30 adversarial fixtures integrated into CI.

## Non-Negotiable Guardrail Invariants

- Motivation can raise exploration budget; it never raises truth confidence.
- Narrative evidence cannot directly satisfy substrate truth requirements.
- `PASS` requires explicit, policy-mandated evidence classes.
- All confidence and verdict upgrades must be reproducible from artifacts.
